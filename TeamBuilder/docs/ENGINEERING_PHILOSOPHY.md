# TeamBuilder: Engineering Philosophy (구현 원칙)

본 문서는 TeamBuilder 프로젝트의 대규모 진화를 위해 준수해야 할 기술적 원칙과 엔지니어링 철학을 담고 있습니다.

## 1. 반투명 엔진 (Translucent Engine)
*   **원칙**: 복잡한 상태 관리는 전문적인 DB를 사용하되, 가독성은 파일 시스템으로 투명하게 제공합니다.
*   **세부 지침**:
    - 모든 동시성 제어 및 영속성 저장은 **`bun:sqlite`**를 사용합니다.
    - DB가 변경될 때마다 비동기적으로 **`state_project.json`**을 최신화하여 사용자가 에디터(VSCode 등)만 보고도 상태를 파악하게 합니다.
    - 사용자가 수동으로 JSON을 수정할 경우, 서버가 이를 감지하여 DB로 다시 동기화하거나 경고를 줍니다.

## 2. 주권적 에이전트 & 클러스터 (Sovereign Agents & Clusters)
*   **원칙**: 에이전트는 독립적인 작업을 수행하고 스스로 업무를 분배할 수 있는 '주체'입니다.
*   **세부 지침**:
    - 개별 에이전트 단위가 아니라 **역할 클러스터(Role Cluster)**로 작업을 위임합니다.
    - 각 에이전트는 자신만의 **작업 큐(In-box)**를 상시 유지하며, 한 번에 하나씩 혹은 병렬로 처리합니다.
    - 작업 위임(Delegation) 시 `source`와 `target`을 명확히 하여 전체 협업 흐름을 추적할 수 있어야 합니다.

## 3. 계층적 거버넌스 (Hierarchical Governance)
*   **원칙**: 에이전트 간 업무 배분은 명확한 권한(Authority) 규정을 따릅니다.
*   **세부 지침**:
    - `Orchestrator` -> `Manager` -> `Contributor` 순의 지휘 계통(Command Chain)을 적용합니다.
    - 자신의 등급보다 높은 에이전트에게 직접 업무를 지시하는 것을 원칙적으로 금지하며, 이는 '보고(Report)'나 '요청(Request)'의 형태로 별도 관리합니다.

## 4. 멱등성과 복원력 (Idempotency & Resilience)
*   **원칙**: 시스템 중단 후 재개되더라도 동일한 상태를 복원할 수 있어야 합니다.
*   **세부 지침**:
    - 모든 과업(Job)의 상태 전이(State Transition)는 원자적(Atomic)이어야 합니다.
    - 작업 도중 장애가 발생하더라도 작업 큐의 상태를 다시 읽어 중단된 지점부터 안전하게 복원될 수 있도록 설계합니다.

## 5. 제로 프릭션 DX (Zero-Friction Developer Experience)
*   **원칙**: 시스템은 최소한의 의존성만으로 빠르고 가벼워야 합니다.
*   **세부 지침**:
    - 별도의 복잡한 ORM보다는 Bun이 제공하는 **고성능 Native SQLite API**를 직접 사용합니다.
    - CLI 명령과 대시보드 조작 사이의 지연 시간을 최소화(0.1초 이내)합니다.
